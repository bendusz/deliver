# v0.13 Codex precision builder specification

Date: 2026-08-22

## Problem

`expert-builder` is well suited to broad implementation work because Opus can hold wide project
context and make architectural judgements. Small bug fixes and tightly bounded implementation tasks
benefit from a second worker optimized for precise code changes. Claude Code needs a safe way to
delegate those tasks to the local OpenAI Codex CLI without weakening pm-skill's sign-off, review,
verification, or Git ownership rules.

## Goals

- Add `codex-builder` as an optional implementation worker beside `expert-builder`.
- Route broad or uncertain work to Opus and precise, locally explained work to Codex.
- Support both initial story implementation and evidence-rich review or gate fixes.
- Keep Claude Code's liaison thin. All write-capable Codex launches go through one bundled runner.
- Make repository effects mechanically reviewable and fail closed when safety state is absent.
- Preserve routing, retries, fix rounds, and parallel worktree location across session loss.

## Non-goals

- Replacing `expert-builder` as the general builder.
- Letting Codex commit, branch, merge, push, or own deterministic gates.
- Giving Codex network access or additional writable repository roots.
- Claiming VM-level containment. The runner closes host temp roots, but remains an OS sandbox.
- Silently falling back from an explicitly selected Codex story.

## Routing contract

Every story declares `Builder: expert-builder | codex-builder | auto`.

- `expert-builder`: broad, architecture-heavy, cross-cutting, ambiguous, or context-heavy work.
- `codex-builder`: one precise outcome, machine-readable bounded `pm-meta.touches`, no open design decision,
  and an exact verification command.
- `auto`: the PM resolves the worker once, records the reason, and persists the result before build.

A localized failing gate or accepted review finding may use Codex even when Opus performed the
initial build. Fix mode requires a contained Markdown evidence brief under `tmp/codex-builder/`.

## Runner requirements

The bundled runner must:

1. Require an absolute path that is exactly the target Git worktree root.
2. Require an in-worktree, non-symlinked, valid `pm/pm-state.json` with `signed_off: true`.
3. Accept only fixed named arguments and reject free-form Codex flags.
4. Validate story and evidence paths with canonical containment.
5. Parse strict one-line `pm-meta` JSON near the story header, cross-check its builder with the
   visible field, and reject unbounded, duplicate, globbed, root-wide, or escaping touch paths.
6. Launch one foreground `codex exec` using `workspace-write`, an ephemeral session, ignored user
   config and execpolicy rules, strict config validation, and explicit overrides that disable
   host temp roots, network, web search, MCP servers, lifecycle hooks, subagents, and login shells.
   Tool commands inherit a reduced secret-filtered environment and receive a worktree-local,
   per-run `TMPDIR` that is removed on exit.
7. Require structured JSON output against a bundled schema.
8. Snapshot tracked and non-ignored untracked contents before and after the run, derive
   `actual_files_changed`, and compare it with Codex's report.
9. Reject any change to `pm/`, stories, the spec, plan, constitution, or a path outside
   `pm-meta.touches`.
10. Fingerprint HEAD, all refs, staged contents, local Git config, and worktree registrations.
11. Bound runtime, handle `INT`, `TERM`, and `HUP`, terminate descendants on a best-effort basis,
    preserve partial edits, and return a distinct timeout or interruption status.
12. Delete successful scratch diagnostics after embedding the result, while retaining diagnostics
    for failures and safety violations.
13. Provide a `--preflight` mode that validates environment, sign-off, capabilities, and optional
    story scope without starting model inference.

## Orchestration requirements

- The PM checks for a clean tree before writing route state or the route log.
- Sequential actor state stores `resolved_builder` until the story ships.
- Each parallel batch entry stores its own `builder` and absolute `worktree`.
- Both builders receive the isolated worktree root in parallel mode. `expert-builder` verifies it
  before editing and uses rooted paths and commands.
- For Codex runs, the PM uses the runner's authoritative changed paths, accumulated across rounds,
  to produce diffs, stage paths, review, verify, and ship.
- Worker switches do not reset retry or fix-round counters and are persisted before retry.
- Deterministic gates, independent review, and `pm-verifier` PASS remain mandatory.

## Acceptance criteria

- Quota-free tests cover unavailable CLI, auth failure, unsigned/missing/symlinked state, canonical
  path rejection, hostile project config, protected and out-of-scope edits, omitted change claims,
  dirty baselines, structured done and blocked output, timeout cleanup, fix evidence, and Git
  metadata mutation including another ref.
- The runner and hooks pass shell syntax and ShellCheck where available.
- Plugin validation checks JSON, frontmatter, executable scripts, templates, hooks, and builder tests.
- An opt-in live smoke test exercises the real CLI in a disposable repository. A separate isolated
  benchmark compares both builders on the same base and story without merging either result.
- README, command reference, changelog, agent contracts, state templates, and orchestration
  references describe the same behavior and limitations.

## Security boundary

The runner treats the repository and its instructions as trusted project input. Session overrides
control safety-sensitive Codex settings. Host temp roots are excluded; necessary tool temp files go
to an ignored run-specific directory inside the worktree. This still is not a VM-level guarantee.
