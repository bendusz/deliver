# v0.20: SpecDD skeleton phase

Status: approved by the user on 2026-09-04 as recommended (per sprint; default none below large; npx specdd init with a bundled fallback). Source: workstream WS5 of
`docs/specs/2026-09-03-v0.16-knowledge-restructure-proposal.md` and the design discussed on
2026-09-03 (optional per-sprint skeleton after sign-off, a `spec-architect` agent, stories pointing
at `.sdd` files, a deviation rule for builders). Writing standard:
`plugins/poteto/skills/unslop/SKILL.md`.

## Purpose

After sign-off the plan's Architecture section is prose, and every story re-describes interfaces in
its own Context. Nothing durable and colocated survives past the build. SpecDD (specdd.ai, npm
`specdd` 1.1.1) puts `.sdd` spec files beside the code they describe, with a root spec and a
`.specdd/bootstrap.md` that tells agents how to read them. A skeleton is that tree written before
the code exists. This release adds an optional Skeleton phase between sign-off and decomposition,
one agent that writes it, and the story, reviewer, verifier, analyzer, and runner changes that let
the rest of the pipeline use it.

## A. SpecDD facts the plugin relies on

- A `.sdd` file beside a code file with the same basename is that file's spec; a directory's spec
  is `<dir>/<dir>.sdd` or a parent-held `<dir>.sdd`. The root spec is `<project-root-name>.sdd` at
  the root. Sections are `Spec:`, `Purpose:`, `Structure:`, `Owns:`, `Can modify:`, `Must:`,
  `Must not:`, `Depends on:`, `Exposes:`, `Accepts:`, `Returns:`, `Raises:`, `Tasks:`,
  `Done when:`, `Scenario:`, `Example:`, used only when useful.
- `.specdd/bootstrap.md` explains the rules to agents; `bootstrap.project.md` and a git-ignored
  `bootstrap.local.md` layer on it. The recommended `AGENTS.md` line is: read
  `.specdd/bootstrap.md` before working on this project and treat specs as source-adjacent
  contracts.
- The CLI (`specdd init`, `update`, `inspect`) is optional and has no validator. The plugin never
  depends on it: when `npx` can run `specdd@1`, the PM offers `specdd init` and `specdd inspect`;
  otherwise the bootstrap comes from a bundled template and inspection is a tree listing.

## B. Delivery mode and scale

- `docs/plan.md` Delivery mode gains `Skeleton: specdd | none`. Default `none` at `tiny`, `small`,
  and `standard`; default `specdd` at `large` and `regulated`. The user can set it either way at
  any scale. Nothing else in this release runs when it is `none`.
- `references/scale-profiles.md` rows say so in one clause each.

## C. The Skeleton phase

New `references/skeleton.md` (under 400 words) owns the phase; `SKILL.md` lists it as phase 4a
between sign-off and decomposition; `/pm-skill:skeleton [sprint]` runs or extends it on demand.

- Runs once per sprint, after sign-off and after scaffold, before that sprint's decomposition.
  Sprint 1 produces the root spec, `.specdd/bootstrap.md` (via `specdd init` or the template), and
  the sprint's module specs. Later sprints extend the tree and may supersede a module spec, never
  delete one.
- Inputs to the agent: the plan's Architecture, Scope, and Stories table for the sprint; the spec
  IDs the sprint covers; the `codebase-analyst` pack on brownfield work; the design-exploration
  sketch when one exists; the wiki index when one exists.
- Output: `.sdd` files only, under directories the code will live in (creating empty directories
  is allowed; creating source files is not), plus the root spec and `.specdd/bootstrap.md` on
  sprint 1. Every module spec carries at least `Purpose`, `Owns`, `Exposes`, `Must`, and
  `Done when`; `Done when` lines are testable and map to spec IDs in a trailing `(FR-…, AC-…)`.
- Checkpoint, not a gate: the PM shows the tree and, when the CLI is available, `specdd inspect`
  output, then logs the phase and loads `decomposition.md`. Sign-off already happened; the
  sign-off hook does not block `.sdd` writes because they are not implementation writes (see F).
- The PM commits the skeleton with the log line, as it commits the scaffold.

## D. The `spec-architect` agent

`agents/spec-architect.md`: model `claude-opus-5`, effort `medium`, tools Read, Grep, Glob, Write,
Edit; body budget 230 words. It writes only `.sdd` files, the root spec, and `.specdd/bootstrap*.md`;
never source, tests, config, `docs/`, or `pm/`. It reads the bootstrap first and follows the
SpecDD vocabulary. It returns the tree it wrote, the modules it superseded, and any plan decision
it could not turn into a spec (a `Must` with no owner, a boundary the plan leaves open), under ten
lines. It never runs git.

## E. Stories, builders, reviewers, verifier, analyzer

- `decomposition.md`: with a skeleton, a story's `pm-meta.touches` are the directories or files
  its `.sdd` files govern (so `[P]` safety derives from `Owns`), its Context names the `.sdd` paths
  instead of restating interfaces, and each acceptance criterion cites the `Done when` line it
  satisfies where one exists. `story.md.template` gains one optional header field on the Risk
  line: `Specs: <.sdd paths|none>`. The readiness checklist gains one item: every named `.sdd`
  exists and its `Owns` covers the story's touches.
- Builders: `expert-builder` and the Codex build prompt read the story's `Specs` before the
  sources. A builder may edit a `.sdd` inside its touches when the implementation forces it, and
  must report the change in its return (`STATUS` line gains `SPECS CHANGED: <paths|none>`). The
  root spec and `.specdd/` are never a builder's to edit.
- Reviewers: the PM passes the story's `Specs` alongside the diff; `code-integrity-reviewer`
  treats a `Must`, `Must not`, or `Exposes` violation as a `major` and an unreported `.sdd` change
  as a `major`; `architecture-reviewer` checks `Depends on` and `Forbids`.
- `pm-verifier`: receives the `Specs`; a `Done when` line for a covered criterion that the diff
  does not satisfy is a `FAIL` with the line quoted.
- `/pm-skill:analyze` (`artifact-consistency.md`), only when `.specdd/` exists: a story criterion
  with no `Done when` and a `Done when` with no story (MEDIUM); a story whose touches fall outside
  its specs' `Owns` (HIGH); an orphan `.sdd` no story or root spec references (LOW); a module spec
  missing `Purpose`, `Owns`, or `Done when` (MEDIUM).
- Wiki: `.sdd` files are raw sources; `knowledge.md` adds them to the first ingest and to the
  post-story ingest list. No new librarian mode.

## F. Hooks and runner

- `hooks/require-signoff.mjs`: `.sdd` files anywhere and everything under `.specdd/` are
  planning artifacts, like `docs/`: the hook allows them whether or not the plan is signed off.
  (The skeleton runs after sign-off anyway; the allowlist records the classification and lets a
  user draft specs before approval.)
- Codex runner: `.specdd/` joins the protected directories in `build.mjs` and `snapshot.mjs`; any
  `.sdd` file at the repository root (no directory component) is protected, which is where the
  root spec lives by convention. A `.sdd`
  inside `pm-meta.touches` is editable by Codex, and its change shows up in `actual_files_changed`
  like any other path. The build prompt tells Codex to read the story's `Specs` and to report a
  spec edit in `summary`.
- `AGENTS.md` scaffold: when `Skeleton: specdd`, the PM appends the recommended SpecDD line to the
  project `AGENTS.md` under Conventions (a fact: where the contracts live). The template gains a
  commented optional line.

## Out of scope

- Bundling or vendoring the `specdd` CLI; validating `.sdd` syntax in the runner.
- Generating stub source files (that is code and fights the gates).
- Nested per-directory `AGENTS.md` files.
- Migrating existing projects' stories to `Specs`; a project turns the skeleton on at its next
  sprint and only new stories carry it.
