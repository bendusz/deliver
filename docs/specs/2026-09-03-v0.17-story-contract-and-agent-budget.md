# v0.17: story contract and agent budget

Status: approved by ruling (the items were found by the v0.16 review rounds and deferred to 0.17.0
in the round 3 fix wave; see `codex/2026-09-03-1752-codex-review-codebase-token-efficiency.md`
findings 2, 3, 4, 6, and 7). Writing standard: `plugins/poteto/skills/unslop/SKILL.md`.

## Purpose

Every story dispatch loads the story file, the project `AGENTS.md`, and one agent body into a
worker. 0.16 made `AGENTS.md` facts-only. 0.17 does the same for the other two: the story header
stops repeating its machine metadata, and each agent body carries only the rules that change what
the agent does. The behaviour of the plugin is unchanged; each dispatch is smaller.

## A. Story contract v2

- `pm-meta` is the only source of a story's builder and touch paths. The visible header no longer
  carries `Touches`, `Builder`, `Security-sensitive`, or `Architecture-sensitive`.
- The visible header is two lines: `Sprint · Priority · Covers · Depends on · Parallel-safe` and
  `Risk · Review lenses`. Security and architecture sensitivity are the presence of
  `security-auditor` and `architecture-reviewer` in `Review lenses`.
- `Context (self-contained)` holds only story-specific facts that `AGENTS.md` does not already state.
- Stories written before 0.17 keep working. The parser treats a visible `Builder:` line or
  `Touches:` field as optional. When one is present it must still agree with `pm-meta`, so a stale
  header cannot mislead a reader; a disagreement is still `blocked`.
- Every reference, command, agent, template, checklist, example, test fixture, and README sentence
  that names the removed fields is updated. `/pm-skill:analyze` derives sensitivity from the lens
  list. `migrations.md` says what a pre-0.17 story looks like and that no migration is required.

## B. Agent bodies

- Each agent body (the text after the frontmatter) fits its budget below. The frontmatter
  (`name`, `description`, `tools`, `model`, `effort`, `color`) is unchanged except where section A
  changes a description's wording.
- Every hard rule, input, tool restriction that the frontmatter cannot express, stop condition,
  and literal token the PM parses survives in exactly one place in the body. Literal tokens:
  reviewer severities `block`, `major`, `minor` and verdicts `PASS`, `CONCERNS`, `FAIL`; builder
  status `done` and `blocked`; verifier `STATUS: PASS | FAIL | UNKNOWN`; Codex wrapper
  `runner_status` values and `UNAVAILABLE`.
- Return contracts:
  - builders: status, the test command and its result, blockers or risks. No diff summary, no
    changed-path list, no follow-ups.
  - reviewers: findings with severity, `file:line`, problem, fix; then the verdict. A clean review
    names the scope it inspected in one line. No praise line.
  - verifier: `STATUS`, then per-criterion and per-gate results with evidence. `FAIL` and `UNKNOWN`
    add the failing IDs and the exact action or evidence needed. No confidence field, no global
    evidence list, no open-issues section.
- `test-engineer` states that it never runs git commands that change repository state.

## C. Runtime trims

- The Codex build prompt keeps: read the story then `AGENTS.md`; implement only that story; the
  build versus fix instruction; run the verification command and relevant tests; one sentence on
  staying inside the listed paths, no network, no git mutation, no PM artifact edits; the reduced
  environment note; the JSON contract. The itemised git subcommand list and the separate
  branch, commit, and pull request sentence go.
- The session hook emits only: a `pm:` line with phase, sprint, and sign-off; a `you:` line; one
  handoff line when a handoff file exists; one `teammate` line per actor whose `current_story` is
  not null, capped at five; the resume pointer. The "this is a PM-managed project" sentence and idle
  teammates go. Legacy-layout messages stay.
