# v0.29: autonomous trust

Status: draft for sign-off, 2026-10-24. Evidence: the eight research reports under `tmp/research/`
(r1 vendor guidance, r2 industry practice, r3 community stances, r4 open-source frameworks, r5 T3
integration audit, r6 self-improvement, r7 verification gates, r8 orchestration). Writing standard:
`plugins/poteto/skills/unslop/SKILL.md`.

## Problem

The user does not review code. Stories ship on the PM's gates, the review panel, and the verifier,
inside T3 Code, at high speed. The review rounds are therefore the only stand-in for a human
reviewer, and their strength is assumed, not measured.

1. **Assurance is unmeasured.** The 0.28 baseline run of `/deliver:agent-evals` never happened. The
   corpus holds six seeded defects for one reviewer. Catching all six bounds that reviewer's miss
   rate at 39% (95% one-sided), which is no claim at all.
2. **Rounds are counted, not calculated.** Two lenses that each catch 80% miss 4% together only if
   their misses are independent. With a miss correlation of 0.5 they miss 12%. Same-model re-review
   is the most correlated case. Nothing in deliver knows which case it is in.
3. **"Cross-model" review is not guaranteed.** `codex-reviewer` runs once per story whatever built
   it, so a Codex-built story can be reviewed by Codex alone on the second-model pass (r7).
4. **The builder can still defeat the oracle.** It may edit or skip the acceptance tests, loosen
   thresholds, or weaken configs. Agents do this in practice (r2 Spotify, r3 Beck, Vincent). The
   scope check sees paths, not intent.
5. **Ship is a prose rule.** Nothing mechanical stops a merge without a verifier `PASS`.
6. **T3 Code steers deliver's agents away from their contracts.** T3's injected instructions tell an
   agent with inherited model options to use `delegate_task` "even for native-supported models"
   (`t3code packages/provider-core/src/server/orchestrationInstructions.ts:39`). This user inherits
   `effort: high`. A `delegate_task` child cannot be made read-only
   (`packages/contracts/src/orchestratorMcp.ts`, `runtimeMode` description), so a reviewer routed
   there loses its `tools:` restriction.
7. **T3 worktrees look like orphans.** `hooks/lib.mjs:265` counts every worktree.
8. **The loop stops when it should continue.** One blocked story halts the sprint, and a stalled PM
   session waits for the user to type `/deliver:resume`.

## Design

### A. The assurance model

Trust is a number per risk tier: the upper bound on the probability that a seeded defect escapes
every layer, measured, with its confidence stated.

- **Tiers.** Each story gets a `Tier`, set in `decomposition.md` from what it changes, beside its
  `Risk`. The tier sets review depth only; `Risk` stays the PM's separate judgement of which merges
  escalate under the checkpoint policy. Three tiers:
  - `T0`: docs, comments, copy, configuration with no behaviour change.
  - `T1`: ordinary behaviour change.
  - `T2`: auth or authz, crypto, secrets, money, data migrations or deletion, public API or schema,
    untrusted input, dependency changes.
- **Targets.** These are defaults a project changes with the Delivery mode line
  `- Assurance targets: T0=0.10, T1=0.05, T2=0.02` in `docs/plan.md`:
  - T0 ≤ 10%;
  - T1 ≤ 5%;
  - T2 ≤ 2%.

  Each bound is a 95% one-sided Clopper–Pearson upper bound on the joint escape rate.
- **What the corpus can prove.** With zero escapes in `n` seeded defects, the bound is about `3/n`:
  - 60 defects prove 4.9%;
  - 100 defects prove 3.0%;
  - 150 defects prove 2.0%;
  - 300 defects prove 1.0%.

  A tier whose target the corpus cannot reach is **unmeasured**.
- **Never cut review without evidence.** An unmeasured tier runs the maximum panel:
  - every lens;
  - the opposite-family reviewer on the first review and on every fix round;
  - two trials of `code-integrity-reviewer` on T2.

  A measured tier runs the cheapest panel whose bound meets its target.
- **The panel in force.** A measured tier's panel always gains the builder's opposite-family lens
  on top (`expert-builder` gets `codex-reviewer`, `codex-builder` gets `code-integrity-reviewer`).
  A tier forced to the maximum panel by OVER TARGET has the maximum panel in force.
- **One named exception: a missing Codex lens.** When a Codex lens a tier's panel needs is
  unavailable (the opposite-family lens, or a calibrated `codex-reviewer`), because Codex is absent
  or refuses, `T0` and `T1` continue with the lenses that can run and record it, and `T2`
  escalates. The Execution block's `panel` records what actually ran, and the trust report counts
  the story as below panel and withholds that tier's bound (§F).
- **OVER TARGET is enforced at sprint start.** The PM reads the latest `--trust` output or the
  Trust section of the latest `docs/retros/sprint-<n>.md`. Any tier flagged OVER TARGET (§F) runs
  the maximum panel until `/deliver:calibrate` re-runs.
- **Joint, not multiplied.** The escape rate of a panel is computed from the set of lenses that
  caught each seeded defect. No independence assumption is made, so correlated blind spots count in
  full.
- **Repeats are lenses.** "The same lens, a second trial" is a candidate panel member. The
  calibration shows whether it adds catches or only cost.
- **False positives cost rounds.** The calibration also records each panel's false-positive rate on
  clean fixtures. A panel whose false-positive rate is unknown cannot be selected. Ties on cost
  break on fewer select escapes, then on lower false positives, then on fewer slots.
- **Layers before review count.** Gates, the test-integrity check, and protected acceptance tests
  run first. The panel is calibrated on defects that survive them, which is the realistic residual.
- **Select on one split, certify on another.** Choosing the cheapest of about 240 panels by their
  bounds on the same data breaks the 95% claim: an unsafe panel wins more than 5% of the time. Both
  reviewers of the first build raised this. Calibration therefore runs in two stages:
  1. The `select` split, with every lens, chooses each tier's panel: the cheapest panel whose
     observed select escape rate is at or below the target. No bound is computed here, because 36
     cases cannot bound anything at 5%.
  2. The `certify` split, with fresh trials of only that panel, gives the bound. Each tier gets one
     test, so there is no multiplicity.

  A tier whose chosen panel lacks complete certify data is unmeasured. So is a tier the certify
  split is too small to reach even with no escapes, which takes 29, 59, and 149 cases for 10%, 5%,
  and 2%. Certification skips that tier. No select trial may be recorded after the first certify
  trial.

### B. Calibration corpus and calculator

- **`plugins/deliver/benchmarks/assurance/`**, separate from `agent-evals`, frozen and pinned by its
  own `MANIFEST.sha256` (checked by `validate.sh`).
  - Each seeded case has `story.md`, `base/` (a tiny Node repo), `defect.patch`, `clean.patch`,
    `class`, and `witness.test.mjs`.
  - The witness test **fails** with `defect.patch` applied and **passes** with `clean.patch`
    applied. That makes every seeded defect provably real without a person reading it.
    `validate.sh` runs every witness both ways.
  - The witness never reaches a reviewer.
  - Classes: correctness, security, criterion-unmet, test-integrity, concurrency or async,
    performance, error handling, data.
  - Clean cases (about 25% of the corpus) carry only `clean.patch`. They measure false positives.
  - Batch 1 ships 100 seeded and 25 clean cases. With the three batch-0 examples, the corpus holds
    102 seeded cases (36 select and 66 certify) and 26 clean cases (11 select and 15 certify). 66
    certify cases with no escapes prove 4.4%, which meets T1. T2 at 2% needs about 150 certify
    cases with no escapes, so it grows by later batches.
  - Each batch is split between Claude and Codex authors, so neither family's lenses are graded only
    on defects their own family wrote.
- **Authorship without a human reader.** A batch is authored by an agent from a different family
  from the lenses under test where possible. It is committed alone, never with a prompt change, and
  admitted only if every witness passes both ways. This relaxes the 0.28 rule that "a person changes
  a fixture".
- **`scripts/assurance.mjs`**
  - `list`: lists the cases.
  - `trial-record`: appends JSONL lines of the form `{phase, lens, model, effort, promptSha256, case,
    trial, caught, falsePositive, tokens}`. The prompt hash is taken when the trial is recorded, and
    duplicate records are refused.
  - `calc`: selects on `select` and certifies on `certify`. It writes each tier's panel, its select
    escape rate, its certify bound, and its status to `benchmarks/assurance/panels.json`, stamped
    with:
    - each lens's model, effort, and prompt hash;
    - the corpus manifest hash.

    A panel goes stale when any of these changes.
  - A tier counts as calibrated only when its certify bound meets the effective target. A panel
    with unknown cost ranks after every priced panel. A panel without complete coverage of the clean
    cases cannot be selected.

  Node ESM only, with tests under `scripts/tests/`.
- **`/deliver:calibrate`**, for maintainers. It runs the lenses over the corpus (two trials each,
  each lens on its relevant classes plus every clean case) and records results. Then it runs `calc`.
  Re-run it when a lens's model, effort, or prompt changes; `panels.json` is invalid for any other
  stamp. Estimated cost for the sprint-1 corpus: about 500 review runs.

### C. Oracles the builder cannot move

- **Protected acceptance tests, mandatory at T1 and T2.** `test-engineer` writes the red acceptance
  tests before the build. Their paths are recorded as `protected:` in the Execution block. Any change
  to a protected path fails the scope check, the Codex runner refuses it, and the builder brief
  says so.
- **Holdout checks at T2.** `test-engineer` also writes extra acceptance checks, into a temp
  directory outside the repository.
  - The PM stores them with `scripts/holdout.mjs` on the private ref
    `refs/deliver/holdout/<project-key>/<story-id>` (`_` for a project at the repository root). That ref is never checked out and never pushed, and no
    builder brief mentions it.
  - At state 5 the PM copies the checks into a temp directory, runs them beside the verifier, and
    deletes the copy. A failure is a `FAIL`.
  - A missing ref on resume means `test-engineer` regenerates the checks.
  - A builder with Bash can still find the ref. The protection is that it is absent from every
    checkout and brief, not that it is secret. This was decided after the round-1 review, which
    found that gitignored files did not survive a resume.
- **`scripts/test-integrity.mjs <base> <head>`**, run by the PM as a gate after every writer run
  at T1 and T2 only; T0 records `integrity: n/a`. It fails on any of these:
  - a deleted or renamed test file;
  - added skip or focus markers across common frameworks (`.skip(`, `.only(`, `xit(`, `it.todo`,
    `@Disabled`, `@Ignore`, `pytest.mark.skip`, `t.Skip(`, `#[ignore]`);
  - a net drop in assertion calls in a modified test file;
  - weakened coverage thresholds, lint rules, `tsconfig` strict flags, or toolchain versions;
  - added disable or ignore pragmas (`pragma-added`);
  - any change to a protected path.

  The output is a JSON verdict. A story that legitimately needs one of these declares it in
  `pm-meta`.

### D. Review by the opposite family

- `review-gates.md`: the panel includes a lens from a family other than the builder's, save the
  missing-Codex-lens exception in §A.
  - An `expert-builder` story gets `codex-reviewer`.
  - A `codex-builder` story gets the Claude `code-integrity-reviewer`, which it always has.
  - A fix written by the other family also triggers the opposite-family lens for that round.
- Fix rounds are re-reviewed by the panel that the tier's `panels.json` entry names, not "the panel
  alone". At T2 unmeasured, that includes the opposite-family reviewer.
- The fix-loop heuristic "more than about 5 means you are not filtering hard enough" goes (r7). The
  PM still triages every finding against the code.

### E. The mechanical ship gate

- A `PreToolUse` Bash hook, `hooks/require-verified.mjs`, gates every `git merge` of a `pm/*`
  story into the integration branch. It allows the merge only when the branch records
  `verifier: PASS <sha>`, and at T1 and T2 also `integrity: pass <sha>`.
  - **Which SHA counts.** The SHA must be the branch tip, or an ancestor of it followed only by:
    - commits that change only the story file, `docs/handoff/*.md`, or both;
    - merges that reproduce `git merge-tree` exactly.
  - **Claim fields are trusted only from the integration branch.** `tier`, `deliver`, `protected`,
    and `integrity_allow` are read from the integration branch's copy, never from the story branch.
    The plan and the approval marker are also read from trusted refs, never from the working tree.
  - **Project resolution.** The merge's own directory, after `cd` or `git -C`, identifies the
    deliver project for a story one project claims. A story several projects claim must be
    verified in each: both gates judge every claimant and refuse when any lacks the verdicts,
    naming it, with "two projects claim this story; verify it in each or rename the branch". From a directory that is in no deliver project (for example a monorepo
    root), a story-like merge blocks with "run the merge from the project directory, or with
    git -C <project>", unless its target is a non-base branch that no found project names as its
    integration branch.
  - **Failure mode.** The hook fails open on unreadable hook input, with the kill switch set, or
    outside a deliver project; the hook header lists the remaining known limits. Once a story
    merge into the integration branch is certain, anything the hook cannot establish blocks.
  - **The git-level gate.** A text parser cannot be complete, so an authoritative gate runs
    inside git, on git's `reference-transaction` hook (git 2.28 or newer).
    `require-verified.mjs` exports `judgeMerge(root, { target, commits })`, the same verdict
    logic as the Bash hook (project resolution, the story a commit belongs to, the claim from the
    integration ref, the verifier and integrity SHAs, the after-verdict rules, the legacy rule,
    the kill switch), and `judgeRefUpdate(root, { target, old, new })`. For an update of an
    integration branch, the latter allows a deletion and a new tip a trusted remote copy of the
    integration branch already holds (only `refs/remotes/<remote>/<integration>`, and an upstream
    only when its merge ref is the integration branch's own name, never a `pm/*` branch);
    otherwise it finds the `pm/*` tips (local, remote, or named in FETCH_HEAD) that `old..new`
    introduces, exact or a commit inside one, and judges them with
    `judgeMerge`; a stale tip of the same story that a newer one contains is dropped, and so is a
    commit inside a tip that an introduced tip already holds (stacked stories). An update whose old
    value is zero is judged from the ref as it stands; only a missing ref is a creation, judged
    against the trusted base refs, commits inside a story tip included unless a non-story ref holds
    them. A story several projects claim is judged in each (project resolution above); with one
    claimant or none, the merge's own directory comes first, and for the git-level gate, which has
    no directory, the top level and then the projects in sorted order. An update that is
    not a fast-forward (an amend, a rebase) is judged from the last commit of old's first-parent
    history that new holds, so an amended story merge is judged again. Every merge in the update
    built on a story tip must then match `git merge-tree --write-tree` of its parents, with
    conflicts and differences confined to the story file, and every other commit on top of a
    story may change only the story file and handoff notes; else "the merge result differs from
    the verified automatic merge; re-verify". The comparison needs git 2.38; on 2.28 to 2.37 it
    alone fails open, and session start and `--check` report "merged-tree check needs git 2.38;
    merges are not compared with the verified automatic merge". An octopus merge of a story is
    refused, by this gate and the Bash hook alike: "merge one story at a time". A story whose
    changes the update copies, a non-merge commit whose `git patch-id --stable` equals one of an
    unshipped tip's own commits or its whole diff from the merge base, is refused, verified or
    not: merge the story branch itself with `--no-ff`. Patches are compared on code alone (story
    files and handoff notes excluded), so a squash whose record conflicted still matches; a
    cherry-pick match does not count when the update's commit sits on a non-story ref and is no
    newer than the story's (the story copied a hotfix). Only unshipped tips whose changed paths meet
    the update's, and the commits the update brings in, are read. A rewrite (old not an ancestor of
    new, new not an ancestor of old) that replaces a commit recording a story's verifier must keep
    the code diff from its base, measured from the commit new builds on that old or a trusted
    remote copy holds. With the same base (an amend) the code trees must be identical; on a new
    base (a rebase) next's code tree must equal `git merge-tree --write-tree --merge-base` of the
    old range onto it (git 2.40 or newer): a conflict confined to story files and handoff notes
    still gives a tree whose code is compared exactly, and a conflict in code resolved by hand is
    refused with "the rebase changed code while resolving a conflict; ship that change as a
    story". Only where `--merge-base` is unavailable are the `-U0` diffs compared byte for byte
    with the `@@` ranges and `index` lines normalised, under fixed diff options (no renames,
    myers, no indent heuristic, user diff config ignored). `from` may also be FETCH_HEAD's head of
    the integration branch from a configured remote, so `git pull --rebase=merges origin main`
    works without tracking config. Copy
    detection keeps `patch-id`, which ignores whitespace; a whitespace-only copy is not found, an
    accepted heuristic gap. Else "rewriting shipped story history changes code; ship the change as
    a story". A rewrite that keeps a story merge old held (`git pull --rebase=merges`) recreates
    the story's commits off next's first-parent line; they are not copies, and rewriteCheck
    judges them. In any rewrite, a story's own work excludes what old holds, by ancestry or by
    patch-id (an earlier merge-preserving rebase recreated it), so syncing past shipped work, or a
    reword, is not a copy; the hotfix exemption applies to squash matches too. Only when old's range holds a merge whose second parent is the story tip and next
    drops that merge (a linear `git pull --rebase`) is the refusal "a rebase is replaying a
    shipped story merge; use git pull --rebase=merges (or git pull --no-rebase)"; any other copy
    gets the copy reason. Commits a trusted remote copy holds are never judged again. A trusted
    remote copy is `refs/remotes/<branch.<integration>.remote>/<integration>` or the branch's
    `%(upstream)`, when its merge ref is `refs/heads/<integration>`; remote names may hold a
    slash, for these and for `pm/*` tips. The message after a refusal names `git merge --abort`, `git rebase --abort`, or
    `git cherry-pick --abort` for an operation in progress, and `git reset --merge` only when the
    index is exactly the refused commit's tree. The PM's claim and protect commits introduce no story and pass. So
    merge commits, fast-forwards, pulls, rebases, resets, `update-ref`, cherry-picks, squash
    merges, `git push .`, and conflicted merges finished with `git commit` are judged alike, and
    `--no-verify` does not skip it. A deny exits non-zero and git aborts the transaction, with the
    recovery the message names (above).
  - **Installation.** At session start in a deliver project, `session-context.mjs` runs
    `hooks/git-hook-install.mjs`. It writes a POSIX sh `reference-transaction` shim, marked
    `# deliver-merge-gate v2` on line 2, into `git rev-parse --git-path hooks`, with the
    installing node and every integration branch the repository's projects name baked in; the
    shim starts node only in the `prepared` phase for a line updating one of those branches. It
    keeps a private copy in `<git-common-dir>/deliver/` that a hook manager can call. It never
    overwrites a hook without the marker on line 2, a symlink, or an unreadable file, and never
    writes a hooks directory in the working tree, outside the git directory (symlinked directories
    resolved), or set by global or system `core.hooksPath`; it reports each, with the lines to add
    right after that hook's `#!` line, which stop with status 1 only on a refusal, do nothing once
    deliver's private copy is gone or `mktemp` fails, and hand a `reference-transaction` hook's
    stdin to the rest of it; for a hook whose interpreter is not sh (read from a symlink's target
    read-only, and assumed not sh when it cannot be read) it prints an sh wrapper that runs the
    gate and then execs the original, renamed `<hook>.local`, and skips it with a message when
    `<hook>.local` is missing or not executable; a symlinked hook always gets the wrapper, so a
    shared target is never edited. The gate refuses with exit status 86 (`REFUSED`, lib.mjs); the
    shim, the wrapper, and the chaining lines pass on only that status, and turn any other failure
    (a node that cannot start) into exit 0 with "deliver: merge gate failed to run (<code>); not
    enforced". Chaining lines from an earlier version are `chained-stale`. A hook that already runs
    deliver's lines, in any hooks directory, is `chained` once it is executable (else
    `chained-inactive`) and, for `--check`, its private copy is current (else `copy-missing`,
    `copy-stale`); `--uninstall` says to remove them. Session start shows brief notes that name the command printing those lines, and
    never cuts a note. On git older than 2.28 it installs
    `pre-merge-commit` and `pre-commit` shims instead, and reports that fast-forwards, squash
    merges, and cherry-picks are not gated (none makes a merge commit), that a story merged with
    any other head is refused, and that a merge commit's staged result is compared only where git
    needs no content merge
    (against `git read-tree -m` of the merge base and both heads); elsewhere only the verdicts are
    checked. `--check` also verifies the shim is executable, its gate script exists, its node
    runs, and the git version, and reports a deliver shim it cannot remove; `/deliver:doctor` runs
    it and repairs. `--uninstall` removes only deliver's shims and sets the local
    `git config deliver.mergeGate off`, which session start honours and `--check` reports as
    disabled, until the installer runs without a flag; `--check --uninstall` is refused. The Bash hook blocks `--no-verify` (and commit's `-n`; merge's `-n` is
    `--no-stat`) and a `core.hooksPath` override on a story merge or pull, and on a commit of an
    in-progress story merge, since the fallback hooks honour it.
  - **Threat model.** The gate catches a PM's honest mistakes: a forgotten verification, a stale
    verdict, a carelessly chained command, a missing tier. The git-level gate judges every update
    of the integration branch, whatever the shell form. Out of scope remain deleting the hook, overriding `core.hooksPath`, `DELIVER_NO_ENFORCE=1`, a fast-forward on git older than 2.28, the merged-result comparison on git older than 2.38 (the verdicts still apply), and pushing straight to the remote. A story commit cherry-picked onto a non-story branch within the same second as the original, then brought onto the integration branch from it, is not counted as a copy, since the gate takes it for a hotfix the story copied. That hotfix exemption relies on commit order, so a forged committer timestamp can defeat it. Deleting the integration branch and recreating it at story history a non-story ref holds is not judged against the deleted value. On git older than 2.40 (no `merge-tree --merge-base`), a rebase over shipped story work is compared by normalised diffs, which cannot tell a change moved to another place in a file from the original.
    Neither gate is a boundary against an agent that evades it on purpose with Bash; the 0.30
    sandbox is.
  - **Remote PR mode is outside it.** The hook does not see `gh pr merge` or a UI merge. Before
    either, the PM confirms the recorded `verifier: PASS <sha>` and, at T1 and T2,
    `integrity: pass <sha>` name the PR head, or an ancestor of it followed only by story-file and
    handoff commits or automatic merges of the integration branch: the rule the hook applies to a
    local merge. The checks, in `environment.md`:
    - `git merge-base --is-ancestor <sha> <head>` succeeds;
    - `git log --stat <sha>..<head> --not origin/<integration>` shows only the story file and
      `docs/handoff/*.md` in non-merge commits;
    - for each merge commit in `git rev-list --merges <sha>..<head> --not origin/<integration>`,
      every conflicted path from `git merge-tree --write-tree --name-only <merge>^1 <merge>^2`,
      and every path in `git diff --name-only <merge-tree-result> <merge>^{tree}`, is the story
      file: the project-prefixed `docs/stories/…` path, or the file whose Execution block names
      the branch. That covers a conflict-free merge with a story-only difference, so the check
      matches the hook exactly (`git show --remerge-diff <merge>` is an alternative view).

    Otherwise the PM re-verifies before merging. That check is prose, a residual risk until a
    later release covers it.
  - `DELIVER_NO_ENFORCE=1` is the kill switch.
- `state.md`: the Execution block gains `tier`, `protected`, `protected_base`, `integrity:
  <verdict> <sha>`, and `verifier: <verdict> <sha>`.

### F. The trust report replaces code review

What the user reads instead of a diff, at each sprint checkpoint, generated by
`scripts/retro-stats.mjs --trust`:
- stories shipped per tier;
- the panel each tier ran;
- `below panel: N`, the stories whose recorded `panel` fell short of the tier panel;
- the calibrated bound, or "unmeasured, maximum panel", withheld while below panel is above 0;
- first-pass stories (no fix rounds, no retries);
- fix rounds;
- integrity blocks;
- holdout failures;
- observed escapes.

It reads these from each story's Execution block on the integration branch, which gains four
fields:
- `panel`: a JSON array of the lens names that ran on every review round, recorded at state 3
  after the first review; a fix round's re-review that runs without a lens drops it from `panel`
  in that round's commit. A lens appears once per trial that ran, so one dispatched twice in a
  round appears twice, as in `["code-integrity-reviewer","code-integrity-reviewer","codex-reviewer"]`;
- `integrity_fails` and `holdout_fails`: integers, default 0, incremented and committed on each
  failure, like `rounds`;
- `updated`: `YYYY-MM-DD HH:MM` in UTC.

The targets come from the plan's `- Assurance targets:` line, defaulting to 10%, 5%, and 2%. The
report opens every checkpoint report at every scale; under the fully autonomous policy it runs at
each sprint boundary into `tmp/log.md` and goes into the completion report.

**Observed escapes.** When later work finds a defect in code an earlier story shipped, the fix
commit carries the trailer `Escaped-From: <story-id>`. `retro-stats` counts escapes per tier against
the stories shipped and reports a Clopper–Pearson bound beside the calibrated one. In a repository
holding several deliver projects, the qualified form `Escaped-From: <project-path>/<story-id>`,
with the project's path from the git top level, names the project outright; a bare trailer counts
for the project whose files the fix commit changes.

OVER TARGET fires when both of these hold:
- at least one escape was observed among stories merged since the calibration in force;
- the bound over those stories exceeds the target.

When it fires, the next sprint runs that tier at the maximum panel until `/deliver:calibrate`
re-runs. That re-run starts a new window. The figure to date is shown for information only.

Requiring at least one escape is deliberate. Zero escapes in a few stories cannot bound anything
under target. Flagging that case would pin every tier at the maximum panel permanently and make
calibration pointless.

### G. Running on its own inside T3 Code

- **Host detection.** At start, the PM runs `ToolSearch select:mcp__t3-code__orchestrator_capabilities`
  and calls it once. On success it loads the new `references/host-t3.md`. Outside T3 nothing changes.
- **Routing precedence**, stated in `SKILL.md` and `host-t3.md`:
  - Every named `deliver:*` agent is dispatched through the `Agent` tool, whatever the host's
    instructions say about inherited model options. Their frontmatter carries the model, the effort,
    and the read-only `tools:` contract.
  - Codex build, fix, and review stay on the bundled runner.
  - `delegate_task` is for Codex advisory and research opinions only. The PM confirms `git status`
    is unchanged afterwards.
- **Worktrees.**
  - `hooks/lib.mjs`, `session-context.mjs`, and `state-health.md` count only deliver's worktrees:
    those under `tmp/worktrees/` or on `pm/*` branches. Other worktrees are reported as host-owned
    and never pruned.
  - The PM refuses to run from a T3 worktree thread whose root checkout holds the integration
    branch, and says why.
- **Continue past a block.** A blocked story no longer stops the sprint while other build-ready
  stories do not depend on it. The PM:
  1. escalates, by a T3 notification when available, with the story and the decision needed;
  2. commits the blocked story's tree to its branch as `wip(<story-id>): blocked`, which never
     ships without a fresh verdict, checks out the integration branch, and takes the next
     independent story;
  3. stops only when every remaining story is blocked or depends on a blocked one.
- **Heartbeat.** After sign-off, under T3, the PM schedules one `schedule_task` interval, by default
  every 30 minutes and bound to its own thread, with the prompt `/deliver:resume --heartbeat`.
  - A heartbeat that finds a turn running, an escalation unanswered, or the sprint at its
    checkpoint does nothing.
  - Otherwise it resumes from git.
  - The PM deletes the heartbeat at project completion or on `/deliver:handoff`.
- **Remote PR mode** (`environment.md`): `link_pull_request`, then `watch_pull_request`. A CI wake
  re-gates locally, and merge still requires the verifier `PASS` and, at T1 and T2, the integrity
  `pass`, both naming the PR head or an ancestor the §E rule allows, checked with the §E
  commands. Afterwards, `unwatch_pull_request`.
- **Doctor.** `/deliver:doctor` under T3 checks four things:
  - whether a custom Claude home hides deliver;
  - whether `node` and `codex` resolve;
  - the Claude Code version;
  - whether the PM thread is in the root workspace.
- **Superpowers precedence.** `SKILL.md` and the README state that when deliver is active, its
  phases replace Superpowers' brainstorming, writing-plans, and subagent-driven-development. TDD,
  debugging, and verification-before-completion remain compatible.
- **Skill-size guard.** `validate.sh` fails when any `SKILL.md` exceeds 16,000 characters, which
  leaves headroom under Claude Code's 20,000-character re-attachment cut after compaction (r4).

## Rules this changes

- **Relaxed:** "a person changes a fixture", replaced by executable witnesses. "Never run `codex`
  outside the runner" now admits advisory and research opinions under T3. Rule 8 worktree cleanup
  is scoped to deliver's own worktrees.
- **Tightened:**
  - Acceptance tests are mandatory at T1 and up.
  - The ship gate is mechanical.
  - Review is opposite-family by construction, with one recorded exception (§A).
  - No review is reduced without a calibrated bound.
- **Kept:** sign-off on the plan, the PM never writes code, the PM runs the gates, PASS, FAIL, or
  UNKNOWN verification, git as the record, no push without a standing permission, and the round and
  retry caps.
