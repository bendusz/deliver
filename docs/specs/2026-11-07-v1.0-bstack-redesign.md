# bstack 1.0: strip deliver back to the basics, T3-first

Status: draft for Ben's approval
Date: 2026-11-07
Supersedes: every `docs/specs/*` and `docs/plans/*` up to v0.29.4 (kept in git history)

## 1. Intent

deliver has grown into about 30,000 lines of skill prose, agents, hooks, a Codex runner,
calibration corpora and tests. Most of it exists to *restrict* agents: read-only tool lists,
snapshot fingerprints, merge-gate parsers, holdout refs, integrity heuristics, tiered review
panels. Ben trusts his agents and treats git as the safety net: every change is a diff he can
read and revert.

T3 Code now gives the host-level primitives deliver hand-built: cross-provider delegation,
nested children, worktree isolation, messaging between threads, completion wake-ups, PR
watching, scheduling, browser and device preview, secret requests. bstack ("Ben's stack", pairing
with the bundled `poteto` pstack) keeps the PM discipline that actually produces good software
and hands everything else to T3 and git.

## 2. Goals, non-goals, anti-goals

**Goals**
- A PM skill whose whole runtime prose (SKILL.md plus references) is under ~800 lines, down from ~2,900.
- Three core roles (builder, reviewer, verifier) and two optional ones (researcher,
  spec-architect), each a short "soul": ground rules, expected return, a *recommended* default
  provider, model and effort that the PM may override per task.
- Every child dispatched through T3. Children may start their own subagents, and may message
  threads the PM names to them.
- SpecDD optional and off by default.
- Sign-off is a conversation step, not a hook.
- No runtime code: no hooks, no tests, no `validate.sh`. The plugin is prose and templates,
  plus one small script, `scripts/log.sh`, that standardises the decision log (§10).
- Trim lands first as deliver 0.30.0; the rename to bstack lands second as bstack 1.0.0.

**Non-goals**
- Running without T3 Code. bstack is T3-only for now. If the T3 probe fails, the PM says
  bstack requires T3 Code and stops.
- Migrating existing deliver projects in place. Old `pm-exec` blocks, handoffs and holdout refs
  are left as inert files (§11).
- Changing the `poteto` plugin's skills. PR 2 edits only poteto's README and PORT.md lines
  that name the marketplace, `deliver`, or removed deliver files, so its install line stays
  correct.
- Re-calibrating reviewers. The calibration result is recorded (§9) and the corpus removed.

**Anti-goals**: it fails even if it technically works when:
- A child's "tests pass" is accepted without the PM running the gates itself.
- A builder reviews its own work, or edits the acceptance tests to go green.
- Agents are restricted by tool allowlists or read-only modes. Trust is the design.
- New ceremony creeps back in: tiers, panels, counters, or phase taxonomies.
- A secret reaches a tracked file. This stays a hard rule in prose, with no scanner.

3. Prefer built-in invocation over bespoke agent definitions. Roles are "souls" with ground

4. Re-evaluate every hard-coded guardrail. SpecDD becomes optional.
5. Sign-off is conversation style.
6. `test-integrity` is removed.
7. T3-only for now.
8. Trim first, rename to bstack after.

## 5. Roles (souls)

Each soul in `roles.md` has four parts: purpose, ground rules (3–6 bullets), return shape, and
the recommended default. The PM pastes the soul, then the story or brief, into the
`delegate_task` `task`. Defaults are recommendations. The PM may pick another model from
`orchestrator_capabilities` when the work calls for it, and records the choice in the story's
Execution block.

| Role | Purpose | Recommended default | Carry over from |
|---|---|---|---|
| builder | Implements one story, a test-only brief, or a fix in its worktree, then stops | Bounded work: Codex `gpt-6-astra`, `reasoningEffort: high`. Broad or cross-cutting work: Claude `claude-opus-5-5`, effort `medium`. Effort up one step on a retry. | `expert-builder.md` scope rules; `test-engineer.md:26-33` test smells; `debugger.md` "reproduce before naming a cause"; Codex prompt in `scripts/codex/modes/build.mjs:24-56` ("nobody can answer questions during this run", result JSON shape) |
| reviewer | Reviews one diff (it runs `git diff` itself) against the story | The family that did **not** build. Claude built → Codex `gpt-6.1-sol`, `high`. Codex built → `claude-opus-5-5`, `medium`. Optional `focus:` line: design, security or performance. | Severity rubric and return shape `code-integrity-reviewer.md:29-50`; focus checklists from `architecture-reviewer.md:18-23`, `security-auditor.md:18-24`, `performance-reviewer.md:31-33`; focus presets `scripts/codex/modes/review.mjs:12-18` |
| verifier | Last gate before merge: each acceptance criterion PASS/FAIL/UNKNOWN against repo and running-app evidence | `claude-opus-5-5`, `medium` | `pm-verifier.md:36-55` (evidence rules, return block). Drop the Bash allowlist premise. |
| researcher (optional) | Answers one external question with a recommendation and a report under `docs/research/` | `claude-opus-5-5`, `low`; Codex `gpt-6-astra` `high` for a second opinion | `researcher.md:21-26` |
| spec-architect (optional, SpecDD only) | Writes `.sdd` files for a sprint | `claude-opus-5-5`, `medium` | `spec-architect.md:21-33` |

Codex-specific rule in `roles.md`/`host.md`: always set `reasoningEffort`. T3's default varies
by model (`low` for `gpt-6.1-sol`, `medium` for `gpt-6-astra`).

Every soul opens with one line: "You are a bstack `<role>` child, not the PM. Do not invoke the
project-manager skill or bstack commands." This matters because a T3 Claude child may load the
plugin.

Gone as roles: codebase-analyst (use built-in Explore), debugger and test-engineer (builder
briefs), the three specialist reviewers (reviewer `focus:`), librarian, technical-writer
(a general-purpose child with a three-line brief), the four Codex wrappers.

## 6. Dispatch, nesting and messaging (host.md)

- **Probe.** At session start the PM loads and calls `orchestrator_capabilities` once. Failure
  means "bstack requires T3 Code" and stop.
- **Default dispatch is `delegate_task`** for every role, so model and effort are explicit and
  every child has a thread the PM can message. Builders use `isolation: "worktree"`. Reviewers
  and verifiers use `isolation: "shared"` and are pointed at the builder's worktree path. Use a
  stable `clientRequestId` of `<story-id>-<role>-<round>` so a retry reuses its child. Quick
  read-only lookups may use the native Explore agent.
- **Nesting.** Any child may start its own subagents (native or `delegate_task`) for work
  inside its brief. The PM does not micro-manage this. The child reports what it spawned in
  its result.
- **Messaging.**
  - Fix rounds go to the *same* builder thread with `t3_thread_send`, so it keeps its context.
  - A brief may name sibling thread ids the child may message, for example a builder asking the
    researcher's thread a question.
  - A builder never messages its reviewer or verifier. Findings always flow through the PM,
    which triages them. This preserves review independence.
  - The PM answers a child's pending question with `t3_pending_request` when the answer is within
    the signed-off plan. Otherwise it escalates to Ben.
  - Every *new* review or re-check is a new `delegate_task`, never a send to an old reviewer
    thread.
- **Waiting.** Async children wake the PM on completion. No polling, no heartbeat schedule.
- **PR mode** (when Ben asks for real PRs): `link_pull_request` + `watch_pull_request`. A wake is
  news, not a merge decision. Merge only on gates plus a verifier PASS at the PR head.
  `unwatch_pull_request` once it is merged or closed.
- **Running-app evidence.** The verifier, or a builder producing evidence, uses `preview_*` /
  `device_*`. Screenshots are saved under `docs/evidence/<story-id>/`.
- **Secrets.** `request_secret` for anything only Ben can provide. Never in a file.
- **Gotcha kept.** Do not run the PM from a T3 worktree thread while the root checkout holds the
  integration branch: git refuses to check one branch out twice (`host-t3.md:93-101` detection).

## 7. Planning flow (planning.md)

1. **Ground.** For brownfield work, run one Explore pass. Dispatch a researcher only when an
   external unknown decides the plan.
2. **Converge.** Ask one question at a time, giving 2–3 options with a recommendation. Unknowns
   are written inline as `[NEEDS CLARIFICATION]`, never guessed.
3. **Write `docs/plan.md`.** It holds Overview, Scope in/out, Requirements with stable IDs
   (FR-n, AC-n, never renumbered), Architecture, the real Commands (test/lint/build), an
   `Integration branch:` line, a Stories table, Risks, and `Skeleton: specdd` only when opted in.
   A separate `docs/spec.md` only when the work will outlive the plan.
4. **Sign-off, conversation style.** Ben says "approved" (or equivalent) in the thread. The PM
   then commits `docs/approval.json` as a record: `{status, approved_at, plan_commit}`. There is
   no hook and no digest. If the plan changes materially after approval, the PM stops, shows the
   diff, and asks again. This absorbs `/correct-course`.
5. **Scaffold.** Add the `@AGENTS.md` bridge and `tmp/` in `.gitignore`, only if absent. Never
   overwrite a user-authored file without showing a diff.
6. **Decompose.** Write vertical-slice story files with `pm-meta` (role, touches), Covers,
   self-contained Context, testable ACs, a verification command, and Depends on.
   Expand/migrate/contract applies for breaking changes. Plan a sprint-1 app-driving check.
7. **Self-check, inline.** Every FR/AC is covered, there are no dependency cycles, and parallel
   stories don't overlap in `touches`. This replaces `/analyze`.
8. **Optional SpecDD.** Only with `Skeleton: specdd`: spec-architect writes `.sdd` contracts per
   sprint before decomposition (`skeleton.md`, `/skeleton`).

Scale guidance is one paragraph in SKILL.md: size the ceremony to the work. A one-story fix
needs no spec and no sprints, just a plan, sign-off, the loop and ship.

## 8. Per-story loop (loop.md)

1. **Claim.** Append the Execution block (`status: claimed`) and commit it on the integration
   branch. The commit must exist before dispatch, because a worktree child starts from the
   parent commit.
2. **Tests first (when the story has testable ACs).** A builder child with a "tests only, red is
   correct" brief writes the acceptance tests, and the PM commits them. The implementing builder
   is told not to edit them. The PM checks `git diff <claim>..HEAD -- <test paths>` before review.
3. **Build.** `delegate_task` builder in a worktree. Record its thread id and branch.
4. **Gate.** The PM runs the plan's test/lint/build itself in that worktree. Never on a child's
   word.
5. **Review.** Opposite-family reviewer on `git diff <integration>...<branch>`, plus a `focus:`
   reviewer when the diff touches auth, untrusted input, hot paths or structure.
6. **Fix.** Triage findings into Fix and Dismissed (with a reason). `t3_thread_send` the Fix list
   to the same builder. A bug fix ships with a regression test that was seen failing. On a second
   identical failure, the builder's next brief is "diagnose, reproduce, then fix". Re-gate, then
   a new review. **Cap: 3 rounds, then escalate to Ben.**
7. **Verify.** Verifier child: each AC is PASS/FAIL/UNKNOWN with evidence. Running-app evidence
   is required where an AC is user-visible. Only an all-PASS proceeds. Record `verifier: PASS <sha>`.
8. **Ship.**
   - Merge the integration tip into the branch and re-gate.
   - Then `--no-ff` merge with a body of Why / Scope / Trade-offs / Blast radius / Verification
     (`implementation-loop.md:194-199`). In PR mode, see §6.
   - Worktree cleanup follows the §15 spike. If T3 cleans up its own worktrees, leave them. If it
     doesn't, the PM removes a worktree it requested only after the merge, only when
     `git status --porcelain` is empty, and only with `git worktree remove` (never `--force`).
     Worktrees the PM didn't request are never touched.
9. **Parallel.** Independent `[P]` stories with no `touches` overlap run as concurrent worktree
   children, at most 3 at once. They are integrated one at a time, re-gating after each merge.
   A merge conflict that can't be resolved cleanly blocks that story and escalates.
10. **Blocked.** When a story blocks, escalate (with a push notification if available), set it
    aside, and take the next unblocked story in the same sprint. Never start a later sprint early.

Hard rules kept in SKILL.md (short):
- The PM never writes implementation code.
- No build before sign-off.
- Git is the record.
- The reviewer is never the builder.
- The PM runs the gates.
- 3-round fix cap.
- No secrets in files.
- Never push, force, or run destructive git without asking.
- Never remove a dirty worktree.

## 9. Review: the calibration result we keep

From `plugins/deliver/benchmarks/assurance/panels.json` (calibrated 2026-10-25 against the frozen
corpus): the measured panel for both T0 (target 10% miss) and T1 (target 5% miss) is a **single
`codex-reviewer` lens**, with a miss-rate upper bound of 4.44% and 0 false positives. T2 was never
measured. The Claude specialist lenses (security, performance, architecture) added no measured
coverage over the generalist. This is the evidence for bstack's default of one opposite-family
generalist reviewer plus an optional `focus:` reviewer.

Caveat: that lens was Codex's built-in `codex exec review` prompt via the runner. A `delegate_task`
Codex child running the reviewer soul is a different, uncalibrated reviewer. Re-measuring it is out
of scope for 1.0.

## 10. State and resume (state.md)

- `docs/approval.json`: `{status: "approved", approved_at, plan_commit}`.
- Story Execution block (`pm-exec`, the marker name kept so it parses old files):
  `{role_model, thread, branch, status, rounds, verifier}` where `status` ∈ claimed, building,
  built, reviewing, fixing, verified, merged, blocked. `thread` is the builder's T3 thread id.
- Resume (`/resume`):
  - Read the approval record, `git log`, the story Execution blocks and `git worktree list`.
  - Map each status to its re-entry point.
  - If a builder thread id is present, `t3_thread_read` it before re-dispatching.
- Branches stay `pm/S<sprint>-<n>-<slug>` across the rename (the prefix is not tied to the name).
- **The decision log, `docs/log.md`, is tracked and committed.** Ben, 2026-11-07: on a project
  that runs for months, it is how he looks back on what was decided and why. It replaces the old
  gitignored `tmp/log.md`.
  - **Written only through `log.sh`.** Every entry is appended by
    `bash "${CLAUDE_PLUGIN_ROOT}/scripts/log.sh" "<message>"`, never by editing the file.
  - **Script contract** (~25 lines of bash, the plugin's only code):
    - It takes one argument: the message.
    - It rejects with exit 1 and a one-line reason on stderr when the message is empty, contains
      a newline, or is **longer than 100 characters**. Characters are counted, not bytes, using a
      UTF-8 locale.
    - It appends one line, `YYYY-MM-DD HH:MM  <message>`, in local time.
    - It writes to the **main checkout's** `docs/log.md`, even when called from a worktree. The
      main checkout is found from `git rev-parse --path-format=absolute --git-common-dir`.
    - It creates the file with a one-line `# Decision log` header if it is missing.
    - It never stages or commits.
  - **What gets logged.** Sign-off, each claim, build, fix round, block and merge, and every
    decision the PM makes without asking. The emphasis is on *why*, for example
    `S2-3: chose SQLite over Postgres, single-user CLI, no server`. A long thought becomes two
    or three lines, not one long one.
  - **Who writes.** Only the PM. Children report back, and the PM decides what is worth a line.
  - **Committing.** The PM stages `docs/log.md` into its next commit on the integration branch,
    whether that is a claim, a round or a merge. It never makes a log-only commit, except one at
    session end if entries are still unstaged. Story branches never touch it, so it cannot
    conflict.
  - It is a history, never a source of state. `/resume` reads its last ~20 lines after git.
  - `templates/log.md.template` is removed. The script writes the header.
  - Ben may already have a `log.sh` of his own. If he shares it, it is adapted to this contract
    rather than rewritten.

## 15. The T3 spike (step 0) and what is left to the builder

**Where it runs:** in this repository, from this PM thread, before package 1. The rest of the
redesign depends on its answers, and it touches nothing tracked. Each probe uses a throwaway
`delegate_task` child with a trivial task, and the PM removes whatever the probe creates
afterwards. The probes:

1. **Worktree location.** Start a child with `isolation: "worktree"` whose task is: create
   `tmp/spike.txt`, commit it on a branch named `pm/spike-0`, and report `git rev-parse
   --show-toplevel` and the branch. Then read back the path and branch from `task_status` and
   `t3_thread_read`, and compare with `git worktree list`. Also check whether T3 removes the
   worktree itself when the child finishes. *Decides loop.md steps 3, 4 and 8, and the cleanup
   rule.*
2. **Resume with context.** `t3_thread_send` to the finished child: "what file did you create?"
   *Confirms fix rounds keep the builder's context.*
3. **Nesting.** A child whose task is to start its own `delegate_task` grandchild and report the
   grandchild's answer. *Confirms children may have subagents.*
4. **Plugin bleed.** Ask a Claude child to list the skills and slash commands it has. *If
   deliver's skill loads in children, the soul's "you are not the PM" line stays essential.*
5. **Codex child.** One Codex `gpt-6-astra` child at `reasoningEffort: high`, given the same
   worktree task as probe 1. *Confirms the default bounded builder works end to end.*

Left to the builder:
