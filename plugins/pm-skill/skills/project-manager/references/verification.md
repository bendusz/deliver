# Verification

The final, independent check that a story is genuinely shippable, run after the deterministic gates
and the reviewer and fix loop and before ship or merge. The `pm-verifier` subagent runs it. There is
no external process and no separate lifecycle, just a read-only Claude Code subagent the PM
dispatches.

## When
In the per-story loop: build, gate, review, fix, **verify**, ship, log. Enter verification only once
the gates are green and no `block` or `major` review findings remain open.

## Inputs to the verifier
- The story file: goal, `Covers:` IDs, acceptance criteria, verification command.
- The `FR-` and `AC-` entries from `docs/spec.md` that the story's `Covers:` line names, and the
  Commands section of `docs/plan.md`. Do not read either document whole.
- The diff text and the list of changed paths.
- The reviewer verdicts and the gate results you already ran.
- If the project has a skill that drives the real app, one generated by
  `poteto:create-verification-skill` at `.claude/skills/verify-<app>/` for example, **you** run it for
  the story's feature before dispatching the verifier, the same way you run the gates, and pass the
  evidence paths it captured: screenshots, transcripts, response bodies. `pm-verifier` is read-only
  and never launches or drives the app itself. It checks that evidence against the acceptance
  criteria instead of reasoning from the diff alone.

## Expected report
`pm-verifier` returns `STATUS: PASS | FAIL | UNKNOWN`, with confidence, per-criterion and per-gate
results, review-finding resolution, open issues, and an action. It treats builder and PM summaries as
claims and checks them against real repo state, using read-only Bash for git, the gates, and grep.

## Handling the verdict
- **PASS** is required before ship. Proceed to commit and merge.
- **FAIL** returns to the fix loop, with the builder, and `debugger` first if a gate is the cause,
  within the same 3-round bound. Then re-verify. Never ship a FAIL.
- **UNKNOWN** means you gather the exact missing evidence the verifier named, a command it could not
  run or an artifact it lacked, and re-verify. If it cannot be obtained, escalate to the user. Never
  treat UNKNOWN as PASS.

## Where evidence lives
- Lightweight or single-story work: a quick inline verifier pass is enough. `STATUS` is still
  required, but you may skip the durable report and checklists and summarise the result in
  `pm/log.md`.
- Non-trivial projects, recommended: write a durable `docs/verification/<story-id>.md` from
  `${CLAUDE_PLUGIN_ROOT}/templates/verification-report.md.template`.
- Optionally tick `docs/checklists/verification-<id>.md` from the verification-quality template.
- Record STATUS, the gate results, and the report link under the story's Verification evidence
  heading, and set `current_story_verification_status` in `pm/actors/<you>.json`.

A story is done only with `pm-verifier` `PASS`; see `review-gates.md`.
